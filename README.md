# 一、缓存基础
## 1.缓存层级
本地缓存:
- 速度快
- 数据不共享
- 内存有限
  
分布式缓存:
- 数据共享
- 容量大
- 速度稍慢
  
数据库/磁盘: 最终数据源

## 2.引入收益与代价
收益：

- 提高读取性能，降低数据库压力。

- 应对高并发，提升系统吞吐量。

- 减少网络/磁盘 IO，加快响应速度。

代价：

- 数据一致性：缓存与 DB 可能不一致，需设计更新策略。

- 复杂性：增加缓存穿透、击穿、雪崩等问题。

- 运维成本：需维护缓存集群，监控命中率等。
## 3.为什么要在DB前面加入缓存?代价是什么？
原因：DB 是系统的瓶颈（磁盘 IO、连接数有限），缓存（内存）能抗住大部分读请求，保护 DB。

代价：

- 引入一致性问题（缓存脏读、更新丢失）。

- 增加架构复杂度（缓存更新、失效、集群）。

- 可能出现缓存三大问题（穿透、击穿、雪崩）。
# 二、缓存更新策略
## 1.旁路缓存读写流程
读：

- 先读缓存，命中则返回。

- 未命中则读 DB，并将结果写入缓存，再返回。

写：

- 常见策略：先更 DB，再删缓存（推荐）；
- 或先删缓存，再更 DB（有并发问题）；
- 或缓存更新（不推荐，写多读少时效率低）。
## 2.为什么先更DB再删缓存
保证DB是最新的，删缓存后，下次读会加载最新的DB值到缓存
# 三、缓存三大问题
## 穿透/雪崩/击穿的现象+方案+对比
| 问题 | 现象 | 核心区别 | 解决方案 |
|---|---|---|---|
| 穿透 | 查不存在的数据，缓存和 DB 都没有，请求直达DB | 数据本身不存在 | 布隆过滤器、缓存空值 |
| 击穿 | 单个热点 Key 过期，大量请求打到 DB | 一个热点 Key 失效 | 互斥锁、逻辑过期 |
| 雪崩 | 大量 Key 同时过期，或 Redis 宕机 | 一片 Key 失效或缓存整体故障 | 随机TTL、高可用Redis(集群、主从)、限流降级 |
# 四、全局ID
## 1.Snowflake位结构
Snowflake（雪花算法）生成 64 位 ID：

- 1 位：符号位（0）。

- 41 位：时间戳（毫秒级，约 69 年）。

- 10 位：机器 ID（5 位数据中心 + 5 位工作机 ID，共 1024 个节点）。

- 12 位：序列号（每毫秒 4096 个 ID）。
## 2.UUID/DB自增/Redis自增/Snowflake对比表
| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| UUID | 本地生成、不依赖中心 | 无序、长、索引差、页分裂 | 非主键追踪 ID |
| DB 自增 | 简单、有序、短 | 扩展差、依赖 DB、分库分表难 | 单机、小流量 |
| Redis 自增 | 高性能、有序 | 依赖 Redis、持久化风险 | 中小规模分布式 |
| Snowflake | 有序、高性能、分布式 | 依赖时钟、需机器 ID 管理 | 大规模分布式系统 |
# 五、锁机制
## 乐观锁和悲观锁区别
- 悲观锁：假设冲突概率高，每次操作都加锁（如  synchronized 、 ReentrantLock 、DB 行锁）。

  - 适用：写多读少，冲突频繁。

- 乐观锁：假设冲突概率低，不加锁，更新时判断版本号（ version ）或 CAS。

  - 适用：读多写少，冲突少。

- 区别：

  - 悲观锁阻塞，乐观锁自旋/重试。

  - 悲观锁保证安全，但性能可能低；乐观锁性能高，但冲突时需重试。
# 六、Redisson
## 1.可重入锁Hash结构
Redisson 的  RLock  基于 Hash：

- Key：锁名。

- Field：线程 ID。

- Value：重入次数（计数器）。

- 加锁：线程首次加锁，Hash 中新增 field，value=1；再次加锁，value++。

- 解锁：value--，为 0 时删除 field。
## 2.Lua三段式
加锁 Lua 逻辑大致为：

- 1. 判断锁是否存在。
- 2. 不存在则加锁并设置过期时间。
- 3. 存在且是当前线程，则重入次数加 1。
- 4. 否则返回锁剩余过期时间。

解锁 Lua 逻辑大致为：

- 1. 判断锁是否属于当前线程。
- 2. 是则重入次数减 1。
- 3. 减到 0 删除锁，并发布解锁通知。
## 3.WatchDog续约
默认锁超时 30 秒，看门狗每 10 秒（ lockWatchdogTimeout / 3 ）检查一次。

若线程仍持有锁，续约 TTL 为 30 秒，防止业务未结束锁已过期。
## 4.MultiLock
MultiLock 是把多个独立锁组合成一个联合锁。

- 所有锁全部加锁成功，才算整体加锁成功。
- 任意一个失败，则释放已成功的锁。
- 适合多资源同时加锁场景。
